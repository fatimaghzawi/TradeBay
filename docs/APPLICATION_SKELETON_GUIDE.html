TradeBay Application Skeleton Guide

Professional architecture document explaining how TradeBay was structured and prepared before (and while) business domains were implemented. Based on the actual repository — not a generic template.

TradeBay is a modular monolith: one FastAPI process + one Next.js app + MongoDB. Domain folders isolate business areas; shared core/shared hold the platform skeleton. README’s original intent: ship scaffolding first, fill commercial workflows domain-by-domain.

1. Project Overview

What this application is

TradeBay is a B2B wholesale marketplace for Lebanese businesses: identity & companies, product catalog/inventory, RFQ→order→shipment procurement, conversations & negotiation, finance & platform commissions, trust/disputes, and AI-assisted sourcing / business planning.

Main architecture

Frontend (Next.js App Router)
        ↓ typed fetch client + httpOnly cookies (credentials: include)
Backend (FastAPI modular monolith, /api/v1)
        ↓ services → repositories (Motor)
MongoDB 7 (replica set rs0 for transactions)

Cross-domain reactions use an in-process event bus (backend/app/shared/events/bus.py) and a shared audit service (backend/app/shared/services/audit.py). AI is behind AIProvider and must not mutate authoritative marketplace state.

Frontend / backend structure

Backend

app/core kernel · app/db Mongo · app/shared kits · app/modules/* domains · app/api/router.py aggregator · app/main.py factory

Frontend

app/ routes · components/ UI · features/ domain entries · lib/api/ clients · providers/ auth/query/theme · lib/navigation.ts shell nav

Technologies

LayerStack (actual)
BackendPython 3.12+, FastAPI, Pydantic v2, Motor, JWT + httpOnly cookies, Pytest, Ruff, MyPy
FrontendNext.js App Router, TypeScript strict, Tailwind, Zod, TanStack Query, ESLint
DataMongoDB 7 via Motor; replica set in Compose
OpsDocker Compose, Makefile, GitHub Actions (.github/workflows/ci.yml)

Database & data access

Document store with one collection per entity enumerated in backend/app/db/collections.py (CollectionName). Access goes through module repositories extending app.shared.repositories.base.BaseRepository (or AppendOnlyRepository for ledgers). No ORM migrations — indexes are idempotent at startup via db/indexes.py.

Authentication / authorization

  • AuthN: email/password → session + JWT access cookie + refresh cookie (hashed at rest)
  • AuthZ: resource.action permission codes on membership role — never if role == "admin"
  • Implemented in identity/dependencies.py (AuthContext, require_permission)

How parts communicate

  • Browser → Next.js pages/components → lib/api/client.ts → /api/v1/...
  • Cookies: tb_access, tb_refresh (core/constants.py)
  • Optional guest header: X-TradeBay-Guest for planner explore paths
  • In-process domain events between backend modules (not a message broker)

Expected request flow (mapped to real code)

HTTP Request
  → RequestContextMiddleware / RateLimitMiddleware / SecurityHeadersMiddleware / CORS
       (core/middleware.py, main.py)
  → Route match on api_router prefix /api/v1
       (api/router.py → module router)
  → Authentication dependency (get_current_user / get_optional_user)
       decode JWT (core/security.py) + session lookup (identity)
  → Authorization (require_permission / require_seller / …)
       AuthContext.has_permission("resource","action")
  → Validation (Pydantic body/query schemas on the endpoint)
  → Controller/Route handler (modules/*/router.py)
  → Service (modules/*/service.py)
  → Repository (modules/*/repository.py → BaseRepository → Motor)
  → MongoDB collection (CollectionName.*)
  → success()/paginated() envelope (shared/schemas/response.py)
  → ORJSONResponse
  → On error: AppError / 422 / 500 handlers (core/exceptions.py)

Optional module mounting (skeleton pattern)

Identity routers are always imported. Other domains use _include_optional("app.modules.<x>.router") in api/router.py so a missing/incomplete module does not crash boot — the hallmark of incremental scaffolding.

5. Database Skeleton

Technology & connection

  • MongoDB 7, Motor async driver
  • MongoManager.connect on app lifespan; ping; ensure_indexes; seed_startup
  • Compose runs mongod --replSet rs0 — required for multi-doc transactions (db/transactions.py)
  • Host URI often needs directConnection=true (see .env.example)

Models / entities

Entities are Mongo documents. Canonical names live in CollectionName (Identity, Catalog, Procurement, Communication, Negotiation, AI Sourcing, Business Planner, Finance, Platform Money, Trust, Settings). Module models.py files describe shapes; persistence is dict-oriented.

Relationships

Reference by ObjectId fields (e.g. business_account_id, user_id, role_id) — not SQL FKs. Uniqueness and lookup patterns enforced with indexes in db/indexes.py (unique email, unique membership user+business, etc.).

Indexes, constraints, migrations, seed

TopicApproach in TradeBay
IndexesIdempotent IndexModel plan at startup — never per request
ConstraintsUnique indexes + service-level invariants
MigrationsNo Alembic-style system; evolve collections carefully + indexes
Seeddb/seed.py — permissions catalog, system roles, platform settings singletons

Where DB logic belongs

  • Repos: filter/sort/update documents, sessions on transactions
  • Service: rules, status machines, cross-collection orchestration
  • Never in routers: raw collection access

Adding a new entity

  1. Add name to CollectionName in db/collections.py
  2. Add indexes in db/indexes.py
  3. Create module repository with collection_name = CollectionName.X
  4. Add models/schemas/service/router as needed
  5. Register router via _include_optional (or hard include)
  6. Add frontend *Api.ts + page if user-facing
  7. Add tests under backend/tests/

6. Authentication & Authorization Skeleton

Concepts (as implemented)

TermMeaning in TradeBayWhere
Authentication Prove who the user is (session/JWT valid) auth_router.py, get_current_user, AuthProvider
Authorization Decide if that user may perform an action require_permission, PermissionGate, nav filters
Roles Named bundles of permissions (per business or platform) roles collection, identity/permissions.py system roles
Permissions Atomic resource.action codes PermissionResource/PermissionAction, permissions collection

Security foundation prepared

  • Password hashing via security helpers (bcrypt; never plaintext) — core/security.py / identity password module
  • Short-lived access JWT; refresh in httpOnly cookie; refresh hashed in sessions
  • Session revocation & refresh rotation — auth service + /auth/refresh, logout routes
  • Cookie names: ACCESS_COOKIE_NAME, REFRESH_COOKIE_NAME
  • Permission resolution: membership → role → role_permissions → set on AuthContext
  • Audit: shared/services/audit.py — domains must not invent parallel audit writers
  • Sensitive log redaction: SENSITIVE_LOG_FIELDS in constants

Protected surfaces

  • Backend: FastAPI Depends(require_permission(...)) on routes
  • Frontend: DashboardGate + AuthProvider protected prefixes + PermissionGate
  • Seller-only: require_seller in catalog for product/inventory mutations

7. Domain / Module Structure

Architecture style: hybrid

Domain-oriented modules (folders under modules/ and features/) inside a layer-oriented skeleton (core → db → shared → router → service → repository). Frontend is also feature-oriented under features/ and components/<domain>. This is a hybrid modular monolith.

Never commit: .env, real SECRET_KEY / JWT_SECRET_KEY, API keys, production Mongo URIs with credentials, Elastic Email keys, webhook secrets. Only commit .env.example with placeholders.

Production hardening (Settings)

When APP_ENV=production, Settings forces secure cookies, rate limiting, debug off; docs URLs disabled; CORS must be an explicit allow-list (no *).

9. Error Handling

Strategy

  1. Services raise AppError subclasses (or domain exceptions extending them)
  2. register_exception_handlers maps to JSON { error: { code, message, details } }
  3. Pydantic validation → 422 VALIDATION_ERROR with sanitized error list
  4. Unhandled Exception → 500 generic message (stack not returned; logged)
  5. Frontend ApiError parses the envelope in lib/api/client.ts

Propagation path

service raises PermissionDeniedError / NotFoundError / …
  → FastAPI AppError handler
  → { "error": { "code": "...", "message": "...", "details": {} } }
  → client.ts normalizeError → ApiError
  → UI FeedbackBanner / toast / login redirect

10. API Skeleton

  • Versioning: all business APIs under API_V1_PREFIX = "/api/v1"
  • Organization: per-domain routers included from api/router.py
  • Request schemas: Pydantic models in module schemas.py
  • Response schemas: success(data) / paginated(items, …)
  • Auth: cookie or Authorization: Bearer
  • Permissions: declared per endpoint via Depends

Real example — create category

From backend/app/modules/catalog/router.py:

@categories_router.post("", summary="Create category")
async def create_category(
    body: CreateCategoryRequest,           # validation
    _auth: Annotated[AuthContext, Depends(
        require_permission("categories", "manage")  # authN + authZ
    )],
    service: Annotated[CatalogService, Depends(get_catalog_service)],
) -> dict[str, Any]:
    return success(await service.create_category(...))
  • Mounted as /api/v1/catalog/categories
  • Requires authenticated user with categories.manage
  • Returns { "data": <category>, "meta": {} }

Health (outside v1 business router)

  • GET /health — liveness
  • GET /ready — Mongo readiness

11. Developer Workflow

Sequence adjusted to TradeBay’s actual architecture:

1.  Define CollectionName (+ indexes in db/indexes.py)
2.  Add permission codes if needed (identity/permissions.py + seed)
3.  Create/extend module: constants → models → schemas → exceptions
4.  Create repository (BaseRepository)
5.  Create service (rules + orchestration)
6.  Create router with require_permission / optional user
7.  Register via api/router.py (_include_optional or hard include)
8.  Add/adjust audit events if security-sensitive
9.  Frontend: lib/api/<domain>Api.ts
10. Frontend: page under app/(dashboard|admin)/… + components/features
11. Wire navigation.ts ROUTES + permissions[]
12. Add unit/integration tests
13. Manually verify authZ (buyer vs supplier vs platform admin)
14. Run ruff / mypy / pytest / frontend typecheck

16. Final Summary

1. Current architecture

Hybrid modular monolith: layered platform skeleton + domain modules + Next.js feature shell.

2. Current folder structure

As in §2: backend/app/{core,db,api,shared,modules} and frontend/{app,components,features,lib,providers}.

3. Core infrastructure already prepared

Config, middleware, envelopes, Mongo lifecycle, indexes, seed, BaseRepository, audit, event names, Identity authz, frontend providers/gates/client, Docker/CI.

4. Domains already prepared / largely implemented

Identity, Catalog, Settings, Procurement, Communication, Negotiation, Finance, Platform Money, Trust, AI provider, AI Sourcing, Business Planner. Marketplace HTTP stub remains.

5. Missing / thin skeleton pieces

  • infrastructure/ mostly empty (ops at root)
  • e2e test folder largely placeholder
  • AI HTTP router still 501 while provider is used elsewhere
  • Observability env vars present but lightly wired (Sentry optional)

6. Architectural inconsistencies

  • Marketplace vs Catalog naming — README “Marketplace” = catalog code; marketplace package is stub/alias
  • Finance README row spans three modules in code
  • Optional includes still used even though most modules now exist (harmless scaffolding leftover)
  • Guest explore softens original “all dashboard gated” assumption for selected paths

7. Technical debt (skeleton-related)

  • Ad-hoc scripts in backend/_*.py (ops helpers) outside package layout
  • Dual “legacy alias” auth routes kept for compatibility
  • No formal migration framework for document shape changes
  • DomainPlaceholder vs fully built screens — some paths may still mix eras

8. What to standardize before continuing

  • Pick one public name: Marketplace ≡ Catalog (document or collapse stub)
  • Keep permission codes as the only authZ check (no role-name branching)
  • Every new entity: CollectionName + indexes + repo + service + router + *Api.ts + tests
  • Prefer service orchestration over cross-importing repositories across domains
  • Treat AI as advisory only (existing rule)
  • Expand integration tests when adding money/procurement transitions
